# Production operations & known limits

What the LucidFence server actually guarantees in production, what has been
**measured** versus **extrapolated**, and where the honest gaps are. Everything
here is derived from the engine (`lucidfence/core/engine.py`), the state store
(`lucidfence/core/state_store.py`), the app paths module
(`lucidfence/core/app_paths.py`), and the performance guard
(`tests/test_perf_engine.py`).

For the safe enforcement rollout see [ENFORCEMENT.md](ENFORCEMENT.md); for
day-2 runbook material see [DAY2.md](DAY2.md) and [RUNBOOK.md](RUNBOOK.md).

---

## Tested limits

**One data point is measured; everything above it is extrapolation.**

The only performance banchmark in the repo, `tests/test_perf_engine.py`, builds
a **10-device, single-fence** simulation tenant and asserts the per-tick p95
stays under a regression ceiling:

- **Fleet size measured: 10 devices, 1 circular fence.** Nothing larger is
  benchmarked.
- A healthy tick is roughly **~0.02 s** locally; the CI ceiling is **0.5 s**
  (`LUCIDFENCE_PERF_TICK_S`), deliberately loose because it is a *regression*
  guard on shared runners, **not** a latency SLA. The metric is the **median of
  a block of ticks, taking the best of up to 3 blocks**: contention noise on a
  shared runner can only make a tick slower, so the best block is the cleanest
  measurement, while a genuine code regression shows up slow in every block.
- The test is a **regression guard**, not a capacity model. It proves the tick
  did not blow up between commits — it does **not** establish a supported fleet
  ceiling.

**No bench exists above 10 devices.** We have no measured data on 100, 1,000, or
10,000-device tenants, nor on many-fence configurations. The per-device cost is
linear in the code path (each device is evaluated against every fence, then
every policy), so cost grows roughly with `devices × fences` and `devices ×
policies` — but that is reasoning about the code, **not a measured curve**. If
you need a supported number for a large tenant, benchmark it on your hardware
first; do not quote a figure this repo has not measured.

The engine runs one cycle per `interval_seconds` (default **900 s / 15 min**).
Cycles are serialized (see idempotency below), so a tick that runs longer than
the interval simply delays the next one rather than overlapping.

## On-disk data model

All tenant state and config are plain JSON/JSONL files under the tenant's **data
dir**. No database, no external service.

### Where the data dir lives

Resolved by `app_paths.data_dir()`:

| Platform | Default location |
|----------|------------------|
| Explicit override | `$LUCIDFENCE_DATA_DIR` (always wins) |
| macOS | `~/Library/Application Support/LucidFence` |
| Linux / other Unix | `$XDG_STATE_HOME/lucidfence` or `~/.local/state/lucidfence` |

The directory is created with `0700` permissions. In the multi-tenant SaaS
layout, each tenant gets its own data dir (e.g.
`data/cloud_tenants/<tenant-id>/data/`).

### Files in the data dir

**State** (written by the engine, safe to treat as derived/rebuildable):

| File | Format | Written | Contents |
|------|--------|---------|----------|
| `device_states.json` | JSON | atomic replace on every upsert | Current `DeviceState` per device — the live fleet snapshot. |
| `events.jsonl` | JSONL | append | Fence/route transition events. |
| `actions_log.jsonl` | JSONL | append | Every remediation attempt (the audit trail). |
| `trails.jsonl` | JSONL | append | Location breadcrumb per device per cycle. |
| `stats_history.jsonl` | JSONL | append | Per-cycle aggregate stats. |
| `dwell.json` | JSON | atomic replace | Per-device dwell seconds/cycles. |
| `action_cooldowns.json` | JSON | atomic replace | Last-executed timestamp per `(device, destructive action)`. |

**Config** (authored/managed, this is what you version and back up):

| File | Format | Contents |
|------|--------|----------|
| `fences.json` | JSON | Geofence definitions. |
| `policies.json` | JSON | Policy DSL (see [POLICY_DSL.md](../reference/POLICY_DSL.md)). |
| `routes.json` | JSON | Route/corridor definitions. |
| `risk_signals.json` | JSON | Optional external risk signals (falls back to the packaged default). |
| `integration.json` | JSON | Optional per-tenant integration config (e.g. Atomic Mail). May contain secrets — see backup note. |
| `cve_feed_<org>.json` | JSON | Cached CVE feed, best-effort. |

**State vs config:** config files are the source of truth you author; state files
are produced by the engine from live location reports and can be regenerated by
letting the engine run again (you lose only historical events/trails/audit, not
the ability to operate).

## Backup & restore

Because everything is files under one directory, backup is a **directory copy**.

**To back up a tenant:** copy its entire data dir while the server is stopped, or
accept a slightly inconsistent snapshot if copying live (the append-only `.jsonl`
files may end on a partial line; readers tolerate that — see below).

- **Minimum to preserve configuration and history:** `fences.json`,
  `policies.json`, `routes.json`, and any `integration.json` / `risk_signals.json`
  you customized, plus the audit trail `actions_log.jsonl` and `events.jsonl`.
- **To preserve full operational continuity** (dwell timers, destructive-action
  cooldowns, current fleet snapshot): also copy `device_states.json`,
  `dwell.json`, and `action_cooldowns.json`.

**To restore:** stop the server, drop the files back into the tenant's data dir,
start the server. The engine loads config and state on startup.

**Limitation — no built-in backup tooling.** There is no `lucidfence backup`
command and no scheduled snapshotting. Backup is your responsibility (cron +
`cp`/`rsync`/`tar` of the data dir). 

**Security note for backups:** `integration.json` can hold credentials. A backup
of the data dir therefore may contain secrets — store it with the same care as
any secret, and never commit it to a repo.

## Idempotency & crash behavior

This is a report of what the code **actually** guarantees, not the ideal.

**Cycle serialization.** `run_once()` takes a non-reentrant cycle lock. If a
cycle is already in flight (the background loop plus an on-demand
`/api/run-once`), the second call **skips** rather than interleaving. Two cycles
never corrupt each other's accumulators or the store.

**Per-file atomicity — partial.** `device_states.json`, `dwell.json`, and
`action_cooldowns.json` are written with the tmp-file + `os.replace` pattern, so
each of those files is individually **atomic**: a crash mid-write leaves either
the old or the new file, never a half-written one. The append-only logs
(`events.jsonl`, `actions_log.jsonl`, `trails.jsonl`, `stats_history.jsonl`) are
plain appends — a crash can leave a **truncated last line**, which every reader
skips (each line is parsed in its own `try/except`). So a single corrupt or
partial record is isolated, never fatal.

**No cross-file transaction.** A cycle is **not** atomic across files. If the
process dies partway through a tick, some devices may be upserted and their
events/actions logged while others are not yet processed. There is no rollback.

**What saves you on restart:**

- The engine re-fetches the full fleet from the location source every cycle and
  recomputes state, so a partially-processed tick self-heals on the next tick.
- Destructive-action **cooldowns are persisted**, so a `wipe`/`lock` already
  issued before the crash will not re-fire after restart until its cooldown
  window elapses.

**What is *not* guaranteed:** exactly-once action delivery across a crash. The
cooldown makes destructive re-issue unlikely within the window, but a crash
between "adapter executed" and "cooldown recorded" can, in principle, allow a
retry. Treat actions as at-least-once, and rely on the cooldown + the audit log
in `actions_log.jsonl` for reconciliation.

## Schema migration (known gap)

**There is no schema versioning.** None of the JSON files carry a `version`
field, and there is no migration step.

What the code does instead:

- **Additive changes are tolerated.** `DeviceState` is a dataclass with
  defaults; new optional fields load fine against old `device_states.json`.
- **Per-record isolation on load.** `StateStore._load` builds each record in its
  own `try/except`; a record that no longer fits the dataclass (e.g. a field was
  *removed* from the schema) is **silently skipped**, not migrated — that device
  simply drops out of the snapshot until its next location report re-creates it.

**Limitation — no upgrade path for breaking changes.** If a future version
renames or removes a persisted field, old state for affected records is dropped
rather than migrated, and there is no tooling to convert files between versions.
Before a major upgrade, back up the data dir; treat state files as regenerable
and config files as the thing to preserve.

## Windows

**The server host runs on Linux or macOS. Windows appears only as a *managed*
fleet, never as the server host.**

- The launcher `scripts/start_all.sh` is bash, and installation/operation assume
  a Unix shell (`brew`/`pip`, `lsof`, `ps`, POSIX signals).
- `app_paths.data_dir()` has explicit branches for macOS (Application Support)
  and Unix/XDG only. **There is no native Windows (`win32`) branch** — on Windows
  it falls through to the XDG path (`~/.local/state/lucidfence`), which is not a
  native Windows location. Running the *server* on Windows is unsupported; use
  WSL or a Linux/macOS host.
- Windows **devices** in the fleet are fully in scope: they are read from and
  acted on through the existing UEM (e.g. the Windows conformidad and
  Workspace ONE adapters). LucidFence correlates and remediates them **through
  the UEM** — it does not enroll, push profiles, or manage the Windows endpoint
  directly, and it never needs to run on the Windows host.

In short: **Linux/macOS to run LucidFence; Windows (and everything else) as the
managed fleet behind the UEM.**
